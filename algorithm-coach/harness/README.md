# Validation Harness

统一的算法验证器：执行某个任务目录下生成的方案，跑一组检查，产出结构化报告。

```bash
python harness/run.py --task knowledge/任务池/<任务名>/ [--profile regression] [--timeout 300]
```

产出两份：

- `validation/report.json` —— 给 agent 读，用于**按错误信息修复**
- `validation/report.md` —— 给人看，也是任务书要求的「验证报告样例」

退出码：`0` 通过／`1` 有 error 级检查未通过／`2` 执行中断（契约不满足、数据取不到等）。

> **命名说明**：这里说的 harness 是**验证器**（execution + validation runner）。
> 它与「agent harness」——指 Pi 这类把 LLM 变成 agent 的运行时外壳——是两回事。
> 本项目两者都有：`pi-main/` 是后者，本目录是前者。

## 接口契约

生成的方案必须实现四个函数：

```python
def load_data() -> pd.DataFrame:
    """返回原始行情。可取数、可读快照。"""

def build_features(df: pd.DataFrame) -> pd.DataFrame:
    """输入原始行情，输出特征表（含目标列）。可用全序列——滚动特征只看历史。
    必须保持行数不变。"""

def fit(train_df: pd.DataFrame) -> Any:
    """只用训练段拟合，返回任意 fitted 对象。"""

def predict(fitted, test_df: pd.DataFrame) -> np.ndarray:
    """只用测试段预测，返回与 test_df 等长的数组。"""
```

目标列名由配置指定（`profiles/regression.json` 的 `target_column`，默认 `target`）。

## 结构性保证（不是检查，是没有发生的路径）

**切分由 harness 掌控，生成的代码碰不到**：harness 按时间切好之后，只把训练段交给
`fit`、只把测试段交给 `predict`。于是下列问题**不会发生**：

| 问题 | 为什么不会发生 |
|---|---|
| 时序任务用随机切分 | solution 拿不到切分权 |
| 标准化用全量数据拟合 | `fit` 只收到训练段 |
| 切分前重采样 | 契约要求 `build_features` 保持行数，越界即报错 |

这三条记在这里而不是做成检查项，是因为它们不是"被检查通过"，而是**根本没有发生的路径**——
把结构性保证伪装成检查项会误导读者以为存在失败的可能。

## 真正需要检查的：切分管不住的那一类

`build_features` 内部仍可能引入未来信息（整表标准化、`shift(-1)`、跨时刻滚动统计）。
这靠接口管不住，但**截断一致性**可以跑出来：

```
F_full  = build_features(df)        # 全量
F_trunc = build_features(df[:t])    # 只喂前 t 行
前 t 行的特征必须逐值相同
```

第 t 行时刻不该知道 t 之后的事，抽掉之后的数据后前 t 行特征就不该有任何变化。
变了就说明用了未来信息。取多个截断点还能定位到**从哪一行开始**不一致。

**目标列按定义就是前瞻的**（未来 h 期收益），故由配置的 `target_column` 排除在比较之外，
否则会永远误报。

## 检查项

| 检查 | 级别 | 依据 |
|---|---|---|
| `interface` | error | 任务书「接口规范检查」 |
| `lookahead` | error | 知识库 `特征与标签时序对齐前视` |
| `runs` | error | 任务书「运行稳定性」 |
| `prediction_valid` | error | 知识库 `预测输出有效性未校验` |
| `timeout` | error | 任务书「运行稳定性」 |

**error / warn 的分界**：error 是"方法错了，结果不可信"，warn 是"结论会偏，需注明"。
把什么都判成 error 会让 agent 陷入无限修复。

计划中但尚未实现的：`determinism`（两次跑结果一致）、`cost_modeled`、`turnover_reported`、
`metric_units`、`naive_baseline`、`target_matches_expected`（由 harness 独立重算标签再比对，
可抓出 horizon 设错这类问题）。它们对应的失效模式目前没有自动拦住，选用时需自行留意。

新增一个检查 = 在 `checks/` 下写一个函数 + 挂 `@check(...)` 装饰器，不用改 `run.py`。

## 交易表现的算法

由 harness 计算，不由方案提供。**同一套策略口径下比较不同方案，差异才归因于模型本身
而不是各自的回测实现**——这也是任务书「多个候选算法方案自动比较」的前提。

- **非重叠周期**：目标是未来 h 日收益，逐日累乘会因窗口重叠而失真，故按 h 为步长取样
- **阈值取自样本内**：用训练段预测的中位数作为持仓阈值，再原样用于测试段。不用固定的 0
  ——知识库 `预测阈值转持仓信号` 卡把"阈值默认 0"列为反例：预测值系统性偏负时，
  固定 0 会让策略几乎全程空仓，交易指标失去意义。阈值取自训练段而非测试段，
  是为了避免"用测试集挑参数"这另一种泄漏
- **只做多/空仓**：A 股不可做空，用 1/0 而非 1/-1
- **摩擦敏感性**：按 `(1-f)^换手次数` 给出不同单边成本下策略收益的上界估算，
  参照知识库 `买入持有基准与摩擦敏感性检验` 卡

## 自测

```bash
python tests/test_harness.py
```

用「正确方案 + 五个故意写错的方案」验证每个检查真的会触发：全样本标准化、特征 `shift(-1)`、
预测恒为常数、预测含 NaN、缺 `predict` 函数。

**验证工具自己不验证，就是个永远通过的摆设。** 上面那个"预测恒为常数"的样本就真的抓出过
一个 bug：用 `np.nanstd(pred) == 0` 判常数，而常数数组的 std 会因浮点累加误差得到极小非零值；
改用 `max - min`（真常数时精确为 0）后修复。

## 与知识库的关系

**每一条检查都指回一张能力卡。** 这意味着 harness 不是凭经验拍出来的规则，
而是把知识库里已经写明的约束**变成机器可执行的强制**——

否则那些约束只是"读到的建议"。实测中发现过这类问题：某次运行的方案引用了
`行情采集容错、限速与增量更新` 与 `数据快照与可复现性约定` 两张卡，却没有落实其中的
重试超时与"取数即落盘"，于是既没有超时保护、重跑又全量重建。**光把约束写在卡里管不住，
写进 harness 才管得住。**
