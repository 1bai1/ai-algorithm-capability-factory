# 行情采集容错、限速与增量更新

## 能力说明
让行情采集链路"取得到、取得全、不被打死"：请求限速、失败重试、接口降级、多源备份补缺、按增量区间拉取。解决免费/公开接口限额、单点接口失效、数据缺段的问题。

## 输入契约
- 数据源与限额前提（原文给过的硬约束）：Yahoo Finance 免费公共 API 每 IP 每小时 2,000 次、每天 48,000 次请求，超限会被拒绝或暂停服务；Tushare 的逐股串行调用易触发限流（具体限额原文未给）。
- 多源备份至少两个独立通道：示例 yfinance（主）+ CoinCodex REST（备）；Binance（主）+ Kraken / Poloniex（补缺）；Yahoo 页面（主，盘前价）+ 当日历史收盘价（备）。
- 增量拉取需要状态：上次抓取时间/起始日期（示例按 `start_date` 抓"某类型最新提交"）、标识映射表（ticker ↔ CIK，对应 A 股的证券代码 ↔ 内部 ID）。
- 请求层需要固定标识与头信息：浏览器 User-Agent、Accept-Encoding、Cookie（反爬场景），代理凭据不得硬编码。

## 输出契约
- 采集结果需带可核对的质量指标：缺失时段占比（示例加密数据集缺失小时占比低于 0.015%）、缺口补齐来源标记录、行数与区间。
- 增量/补缺的落库方式：以唯一键 upsert 写入（避免重复插入）；补缺后的主数据与"补缺中间稿""全集"分文件保存（示例 crypto_data.csv / crypto_force.csv / cryptotoken_full.csv 三层）。
- 采集失败时的降级输出：主接口失败仍能返回备用接口的值（示例：盘前价失败 → 取当日历史数据最新收盘价）。
- 数据源缺陷声明：公开数据集可能自带"尽力去重但不保证完整性"的免责说明，必须作为已知风险记录，而不是当作已校验数据。
- 限速实现的输出副作用：空循环延时会拉长整体采集时间，逐股串行全市场扫描的效率极低。

## 依赖
requests（或数据源 SDK）、json；tushare / yfinance；time（限速，原文用 `Wait(n)`）；os（目录与凭据）；数据库客户端（MongoDB upsert 等，落库场景）。

## 适用条件
- 全市场或大票池批量拉取（逐股调用、免费额度受限）时必须限速。
- 单一接口有停机/改版/封禁风险时，用双通道与降级兜底。
- 数据存在已知缺段（交易所停机、采集失败）时，用多源补齐并把缺失率作为质量指标。
- 需要长期每日更新的数据管道（增量拉取 + upsert 落库）。

## 不适用条件
- 一次性小样本取数（几十行、单标的）：加限速与重试属过度设计。
- 需要严格一致的价格口径时直接跨源拼接：不同交易所的同小时价格可能不一致，原文只说"确保一致性"，未给校验与去重方法，直接拼会污染数据。
- 依赖网页结构解析的取价方式：页面改版即失效，且原文的代理/凭据已失效，不可照搬（合规风险另计）。
- 用空循环延时替代真正的限速与退避：不可靠，遇到限流仍会失败。
- 需要确定重试上限与缓存策略的生产环境：原文未给出这些参数，须自行补足。
